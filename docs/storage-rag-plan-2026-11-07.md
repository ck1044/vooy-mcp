# 미디어 저장소 및 멀티모달 RAG 연동 개발안

기준일: 2026-11-07. 개발 기획안이며 이 문서 작성으로 저장소나 DB를 배포하지 않는다.

상세 기능·데이터 모델·API·개발 작업·완료 기준은 [개발 실행 기획서](superpowers/plans/2026-11-07-vooy-media-storage.md)에 정리했다. 구현 기준은 상세 기획서 v1을 따른다.

## 권장 결정

원본 파일 저장소 + 전용 PostgreSQL/pgvector + 기존 MCP 서버로 구성한다. 별도로 개발 중인 RAG는 작업 API로 연결한다. 원본 저장과 검색용 파생 데이터의 수명을 분리한다.

현재 Docker에는 PostgreSQL 16 및 pgvector 기반 서비스가 운영되고 있다. 이 프로젝트에는 별도 컨테이너, 계정, DB, 볼륨을 배정한다. 확인 시점 여유 공간은 Ubuntu 약 817 GiB, D 드라이브 약 923 GiB다. 이 값은 용량 계획 참고치이며 실제 파일 규모와 보존 기간은 추후 확정한다.

## 저장 구성

| 대상 | 저장 위치 제안 | 역할 |
|---|---|---|
| 이미지·영상·오디오·문서 원본 | `/mnt/d/VOOY/media` | 원본 바이트, 버전, 체크섬 보존 |
| 썸네일·프레임·추출 텍스트 파일 | 같은 저장소의 별도 키 | 원본에서 재생성 가능한 파생물 |
| 직접 입력한 텍스트·검색 청크 | PostgreSQL | 내용, 검색, 출처 연결 |
| 자료 정보·태그·컬렉션·작업 상태 | PostgreSQL | 자료 목록과 처리 상태의 기준 |
| 임베딩 벡터 | PostgreSQL + pgvector | 모델별 검색용 표현 |
| PostgreSQL 데이터 | Docker named volume | DB 파일 관리 |

초기에는 로컬 파일 저장 어댑터를 구현한다. DB에는 절대경로 대신 저장 백엔드와 객체 키를 저장해 이후 S3 호환 객체 저장소로 전환할 수 있게 한다. 영상 원본을 PostgreSQL 바이너리 컬럼에 넣는 방식은 기본안에서 제외한다. 원본과 DB는 별도로 백업하고 실제 복구 시 자료 ID와 체크섬이 일치하는지 검증한다. 같은 디스크의 사본은 장치 장애에 대비한 백업으로 계산하지 않는다.

기로기 SNS 영상으로 사용되는 파일은 기존 `/mnt/d/GIROGI/reels` 보관·운영 편집실 등록 기준을 적용한다. 해당 자료가 이 저장소에도 필요하면 기존 보관 위치와 출처를 명시적으로 연결한다.

## 데이터 모델

- `assets`: 자료 ID, 소유 범위, 미디어 종류, 제목, 출처, 생성 시각, 상태.
- `asset_versions`: 원본 버전, 객체 키, MIME, 바이트 수, SHA-256, 폭·높이·길이, 텍스트 본문 또는 본문 객체 키. 기존 버전은 덮어쓰지 않는다.
- `collections`, `asset_collections`, `asset_tags`: 자료 묶음과 분류.
- `artifacts`: 썸네일, 영상 프레임, 자막, OCR 등 파생물. 원본 버전 및 추출기 버전에 연결한다.
- `segments`: 임베딩·검색의 단위. 텍스트 구간, 문서 페이지, 이미지 영역, 영상 시작·종료 시각, 음성 구간 등의 위치 정보를 가진다.
- `embedding_spaces`: 모델 식별자/개정판, 차원, 거리 척도, 정규화, 전처리 버전, 모달리티, 단일/다중 벡터 표현.
- `embeddings`: 구간 ID, 임베딩 공간 ID, 필요 시 벡터 순번, 벡터와 생성 작업 ID. 호환되는 공간별로 차원 지정 테이블·파티션 및 인덱스를 설계한다.
- `ingestion_jobs`: 추출·임베딩 작업, 상태, 시도 횟수, 임대 만료, 오류 요약, 입력 버전, 결과 버전.
- `upload_sessions`: 업로드 권한, 대상 자료, 예상 크기·형식, 만료, 업로드 및 확정 상태.

모든 자료·작업은 소유 범위를 갖는다. 초기에는 대표 1인 저장소로 시작하되 사용자/MCP 토큰과 소유 범위를 연결한다. 다른 모델·차원·전처리로 만든 벡터는 동일한 유사도 검색에 섞지 않는다. 같은 모델 이름이어도 이미지와 텍스트가 같은 공간인지 RAG 개발 측과 확인한다.

## 저장 흐름

1. MCP가 업로드 세션을 만들고 업로드 페이지 주소를 반환한다.
2. 브라우저 또는 파일 전송 클라이언트가 파일을 HTTP 업로드 API로 보낸다. 영상은 분할 업로드와 재개를 지원한다.
3. 임시 위치에 저장한 파일의 실제 크기·MIME·체크섬을 검증한다.
4. 파일을 최종 키로 확정하고 DB의 자료 버전과 후속 작업을 기록한다. 파일/DB가 한 트랜잭션이 아니므로 중간 실패 복구와 미확정 파일 정리 절차를 둔다.
5. 자료는 저장 완료 상태로 먼저 사용할 수 있고, 추출과 임베딩 상태는 별도로 표시한다.

MCP 도구 인수로 대용량 Base64 파일을 전송하는 방식을 기본 업로드로 삼지 않는다. Vooy 대화 첨부파일의 다운로드 주소를 MCP가 받을 수 있는지는 실제 첨부 연동 시험으로 확인한다. 이 확인과 독립적으로 브라우저 업로드를 제공한다. URL 가져오기는 별도 작업으로 실행하며 크기·시간 제한, 리다이렉트와 대상 주소 검증을 적용한다.

짧은 텍스트는 MCP에서 바로 저장한다. 긴 텍스트와 문서는 파일 업로드 경로를 사용한다. 중복 업로드는 소유 범위와 체크섬으로 검출하되 제목·출처 등의 독립 기록을 보존할 수 있게 한다.

## 별도 RAG와의 계약

RAG 워커는 DB 직접 수정 대신 작업 API로 입력 버전과 원본 접근 권한을 받고 결과를 제출한다.

- 작업 요청: `asset_id`, `asset_version_id`, 입력 종류, 원본 접근 정보, 요구 파이프라인 버전, 멱등 키.
- 결과 제출: 작업 ID, 원본 버전, 추출 구간과 위치, 파생물 참조, 임베딩 공간 정보, 벡터 배치.
- 검증: 소유 범위, 현재 작업 임대, 원본 버전, 차원, 유한 숫자, 벡터 개수, 중복 제출.
- 상태: 대기 → 처리 중 → 완료/실패. 실패 작업만 재시도하며 임대 만료 작업은 회수한다.
- 결과 묶음은 모두 저장·검증된 후 활성화한다. 재임베딩 중 기존 검색 결과는 유지하고 새 버전 활성화 시 교체한다.
- 자료 삭제 시 검색에서 먼저 제외하고 원본·파생물·벡터 정리를 추적한다. 삭제 전 시작된 작업의 늦은 결과가 자료를 복원하지 않도록 버전을 검증한다.

RAG 코드와 모델이 확정되기 전에는 임베딩 공간 메타데이터와 결과 수신 계약을 준비한다. 실제 벡터 컬럼/인덱스는 해당 모델의 차원·표현에 맞춰 마이그레이션한다. 대량의 다중 벡터를 생성하는 모델이라면 자료 수가 아닌 총 벡터 수와 검색 지연을 기준으로 pgvector 적합성을 측정한다.

## MCP 기능

1차: `save_text`, `create_upload`, `finalize_upload`, `get_asset`, `list_assets`, `get_download_link`, `update_asset_metadata`, `delete_asset`, `get_ingestion_status`.

2차: `import_from_url`, 컬렉션 관리, 파생물 조회, RAG 처리 요청 및 재처리.

RAG 연결 후: `search_assets`. 검색 결과는 원본 ID, 버전, 관련 텍스트/썸네일, 문서 페이지나 영상 시간 구간, 접근 링크를 함께 반환한다. 질문 임베딩은 별도 RAG 서비스가 생성하며 동일한 임베딩 공간에서 검색한다. 한국어 키워드 검색 품질은 별도 검증해 벡터 검색과 결합한다.

## 개발 순서와 완료 기준

1. 저장 기반: 전용 PostgreSQL/pgvector, 로컬 저장 어댑터, 마이그레이션, 소유 범위. 서버 재시작 후 DB와 파일 유지 확인.
2. 업로드·관리: 이미지·영상·텍스트 저장, 재개 가능한 업로드, 파일 목록/상세 및 다운로드. 중복·손상·중단·삭제 시험.
3. MCP 연결: Vooy에서 업로드 링크 발급, 텍스트 저장, 목록 조회, 다운로드, 삭제 확인. 브라우저 업로드와 Vooy 첨부 가져오기를 구분해 검증.
4. RAG 연동 기반: 구간·모델 등록·작업 API·배치 결과 수신. 테스트 벡터로 차원 불일치, 재시도, 늦은 결과, 원본 버전 변경 시험.
5. 실제 RAG 연결: 개발 중인 모델로 텍스트→이미지, 텍스트→영상 구간 등의 실제 검색을 평가. 모델 특성에 맞는 인덱스를 선택한다.
6. 운영: 고정 HTTPS 주소, 파일 전송 경로의 업로드 한도/타임아웃 검증, 저장공간 확인, DB와 파일 백업·복구 시험.
